Du mockup à la production

L'architecture en 8 couches pour servir
Faris, Youssef, Nadia, Sarah… et après.

Une stack pragmatique, alignée sur l'écosystème Microsoft d'OCP, conçue pour shipper un MVP en 8-10 semaines avec une seule persona, puis dérouler les personas suivantes par incrément, sans refactor.

2Le cycle de vie d'une question

De *"où en est-on niveau budget OPEX consommé ?"* tapé sur le téléphone de Faris jusqu'à la réponse affichée avec ses 3 KPI et ses sources — sous 3 secondes cible.

1

Auth & contexte

SSO Azure AD, périmètre d'accès (qui peut voir quoi).

2

Routing

L'agent classe la question : Q&A, action, rapport, recherche.

3

Retrieval

BM25 + vector + reranker, filtré par les droits du user.

4

Composition

Construit le contexte LLM avec docs + métadonnées + structure attendue.

5

Génération

LLM produit la réponse structurée (KPIs, bullets, sources, décisions).

6

Trace & log

Langfuse : latence, coût, sources retournées, feedback user.

3Les 6 vrais cailloux (ce qui plante les projets)

L'IA est la partie facile. Ce qui décide du succès, c'est presque toujours ailleurs.

Permissions / ACL critique

Faris ne doit pas voir les fiches paie. Nadia ne doit pas voir le pipeline M&A. À gérer avant le retrieval, pas après.

→ Pre-filtering au niveau du retrieval + audit chaque appel.

Fraîcheur des données fort

Calendrier temps réel, docs en horaire, SIRH en nocturne. À designer J1, pas en V2.

→ Webhooks Graph + batchs Prefect + SLA par source.

Qualité des sources fort

Si les N-1 déposent rien ou taggent mal, l'app retourne du vide. Le mockup le simule, la prod le subit.

→ Convention de nommage + "Sentinel d'ingestion" qui alerte sur les sources manquantes.

Hallucinations sur chiffres critique

Un dirigeant ne pardonne pas un chiffre inventé. Le LLM ne doit pas inventer de KPI.

→ Citations obligatoires + extraction structurée (les chiffres viennent d'un sheet, pas du LLM).

Latence élevé

Sous 3 s ou il ferme l'app. Le streaming masque, mais ne résout pas tout.

→ Streaming + cache + pré-calcul des briefs récurrents (à 6h, pas à la demande).

Adoption critique

L'app c'est 20%. Les 80% c'est sponsor exécutif + training EA/dirigeant + KPI d'usage hebdo.

→ Adoption owner dédié + 1 dirigeant ambassadeur + revue hebdo des usages.

6High-level design hybride — Maestro

Stack hybride par design pour respecter la souveraineté des données sensibles (mailbox du CEO, mémoire stakeholder, briefs) : Azure West Europe pour le compute et l'IA, MongoDB Atlas EU pour le stockage des données sensibles avec Queryable Encryption, Exchange on-prem Group comme source de vérité jamais déplacée.

● On-prem Group

Source de vérité

LAN OCP Group · jamais exposé Internet
  • EWSExchange Server (mail, calendrier, contacts, GAL) — accédé par EWS via service account dédié
  • SPSharePoint on-prem si applicable (notes Comex, dossiers réunion)
  • ADActive Directory Group — synchronisé avec Azure AD pour le SSO
  • FWFirewall / proxy Group — règles ouvertes vers le tenant Azure D²nAI uniquement
● Azure West Europe

Compute & IA

Subscription D²nAI · réseau privé (VNet)
  • PWAFrontend · Azure Static Web Apps + CDN (HTML/CSS/JS — votre mockup)
  • APIFastAPI sur Azure Container Apps (orchestrateur, auth, routing)
  • AGTAgent LangGraph · Container Apps (tool calling, mémoire courte)
  • LLMLLM · modèle maison hébergé Azure ML + Claude Sonnet 4.6 (Anthropic Azure ou API) en fallback
  • EMBEmbedding service BGE-M3 (multilingue FR/EN/AR)
  • SYNPrefect · ingestion EWS → embeddings → Atlas
  • OBSApp Insights + Langfuse auto-hosted (traces LLM, coût, latence)
  • KVAzure Key Vault (secrets, certificats EWS, clés Atlas)
  • AADAzure AD Group (SSO Sarah — réutilise compte OCP)
● MongoDB Atlas EU

Données sensibles

Région Frankfurt · CMK + Queryable Encryption
  • VECAtlas Vector Search — embeddings des mails, briefs, docs (jamais en clair côté Azure)
  • MEMStakeholder Memory (Tanaka & co) — fiches relationnelles avec champs sensibles chiffrés
  • DOCBriefs & rapports générés (historique, versioning)
  • LOGAudit trail immuable — qui a demandé quoi, quelles sources retournées, à quel moment
  • CMKCustomer-Managed Keys via Azure Key Vault (les clés ne quittent pas le périmètre OCP)
  • QEQueryable Encryption sur les champs sensibles (noms, sujets, chiffres) — recherche sans déchiffrer

Connectivité — uniquement des liens privés, jamais d'Internet public

On-prem↔Azure Azure ExpressRoute ou VPN site-to-site. Endpoint EWS Exchange exposé uniquement vers le VNet D²nAI. Mutual TLS, certificats KeyVault.
Azure↔Atlas Azure Private Link + VNet Peering. Atlas n'expose pas d'IP publique. CMK gérées dans Azure Key Vault → les clés restent côté OCP.
Sarah↔Frontend SSO Azure AD tenant Group. Sarah utilise son compte OCP. Sa délégation Outlook sur Faris est portée par son token (pas de service account élevé).
Backend↔LLM externe Si Claude API : appel via Anthropic sur Azure Marketplace (même région EU, mêmes garanties data residency, no-training-on-data). Sinon 100% maison sur Azure ML.

Principe directeur : les données sensibles (mails du CEO, mémoire stakeholder, briefs) vivent dans Atlas avec Queryable Encryption et clés CMK gérées par OCP. Les données techniques (config, cache, métadonnées) restent dans Azure. Les sources brutes (mailbox Exchange) ne quittent jamais le on-prem. Atlas et Azure sont reliés par des liens 100% privés.
